# Open source, лицензирование и governance Voople

Статус документа: decision proposal. Он не является лицензией и не выдаёт
никаких дополнительных прав на код, бренд или ассеты.

## 1. Текущее состояние и цель

Репозиторий публичный, но в нём пока нет `LICENSE`. Следовательно, исходники
можно читать и обсуждать, однако явного разрешения копировать, изменять или
распространять их нет. Такое состояние допустимо только как короткий переходный
этап: оно не является полноценной open-source моделью и затрудняет внешние
вклады.

Цель Voople — дать сообществу возможность проверять код, исправлять продукт и
создавать совместимые расширения, одновременно не позволяя закрытому hosted
форку забрать серверные улучшения и выдавать себя за официальный Voople.

## 2. Решение, предлагаемое владельцу

После прохождения ворот из раздела 4 рекомендуется:

1. лицензировать собственный программный код как `AGPL-3.0-only`;
2. сохранить возможность отдельной коммерческой лицензии для тех, кому нужен
   закрытый производный продукт или встраивание без требований AGPL;
3. защищать имя, логотип и визуальную идентичность отдельной trademark policy;
4. лицензировать first-party ассеты отдельно и явно; отсутствие записи для
   ассета означает, что право на повторное использование не выдаётся;
5. принимать внешние изменения только после подписания CLA, которое разрешает
   владельцу продолжать dual licensing, и подтверждения происхождения вклада
   через DCO sign-off.

`AGPL-3.0-only` выбран как основной кандидат из-за сетевого copyleft: оператор
изменённой доступной по сети версии обязан предложить её пользователям
соответствующий исходный код. Это лучше соответствует серверному социальному
продукту, чем copyleft, срабатывающий только при передаче бинарника.

### Рассмотренные варианты

| Модель | Плюсы | Риск для Voople | Решение |
| --- | --- | --- | --- |
| AGPL-3.0-only + commercial | Hosted-изменения остаются открытыми; возможны платные исключения | Выше порог для части компаний и интеграторов | Рекомендуется |
| MPL-2.0 | Понятный file-level copyleft; проще внедрение в закрытые продукты | Закрытый hosted-конкурент может держать значительную часть продукта вне MPL-файлов | Резерв, если adoption важнее защиты hosted-продукта |
| Apache-2.0 | Максимальная совместимость, явный patent grant | Почти не защищает от закрытых форков | Не соответствует текущей цели |
| Собственная source-available лицензия | Можно сформулировать коммерческие ограничения | Не является open source; сложнее доверие и совместимость | Не использовать под названием open source |

`-only` делает набор условий предсказуемым. Переход на `-or-later` допустим
только отдельным решением владельца после оценки будущих версий лицензии.

## 3. Границы лицензирования

### Программный код

- Репозиторий получает один корневой `LICENSE` после решения владельца.
- Каждый новый исходный файл наследует корневую лицензию; boilerplate-заголовки
  по всем файлам не требуются.
- Сторонние зависимости не перелицензируются. Их лицензии учитываются в SBOM и
  `THIRD_PARTY_NOTICES.md` для распространяемых web/desktop/mobile артефактов.

### Бренд и официальность

- `Voople`, логотипы, иконка приложения и обозначения официальных сервисов не
  должны автоматически подпадать под кодовую лицензию.
- `TRADEMARKS.md` должен разрешать правдивые ссылки на совместимость и запрещать
  форкам создавать впечатление официального релиза, аккаунта или сервиса.
- Форк может работать под своим именем и собственными визуальными активами.

### Визуальные и пользовательские ассеты

- Для каждого first-party набора хранится manifest: автор/источник, право на
  распространение, допустимое изменение, коммерческое использование и версия.
- Пользовательские/creator-ассеты регулируются отдельными Creator Terms: автор
  сохраняет права и выдаёт Voople оговорённую лицензию на хранение, обработку,
  показ и продажу. Кодовая AGPL к этим работам автоматически не применяется.
- Ассет с неизвестным происхождением не включается в публичный source bundle и
  production release до проверки.

### Инфраструктура и данные

- Схемы, миграции и локальное окружение могут оставаться в открытом репозитории.
- Production-секреты, provider consoles, signing material и пользовательские
  данные не являются частью open source и хранятся только в защищённых системах.
- При необходимости приватная operational-конфигурация живёт в отдельном
  закрытом репозитории, а не в скрытой ветке публичного репозитория.

## 4. Ворота до добавления LICENSE

Все пункты обязательны:

- [ ] Подтвердить, кто владеет каждым существенным блоком кода, включая ранние
  коммиты, оплаченные работы и код, созданный в рамках иных договоров.
- [ ] Проверить трудовые/подрядные договоры на IP assignment и право владельца
  публиковать и dual-license результат.
- [ ] Составить реестр first-party и third-party визуальных/звуковых ассетов;
  удалить или заменить материалы без подтверждённой лицензии.
- [ ] Получить список лицензий npm/Cargo и проверить release bundle на
  copyleft/notice obligations.
- [ ] Определить юридическое лицо или физическое лицо — владельца copyright,
  trademarks, commercial licensing и CLA.
- [ ] Утвердить точный вариант: `AGPL-3.0-only` либо документированная альтернатива.
- [ ] Проверить итоговые `LICENSE`, `TRADEMARKS.md`, CLA и Creator Terms у юриста
  в применимой юрисдикции.

До прохождения ворот нельзя принимать значимые внешние PR: без корректного
contributor agreement они могут лишить владельца возможности выдавать
коммерческую лицензию на объединённую работу.

## 5. Contribution и governance

### Начальный режим

- Maintainer-led governance: архитектурные, security, data-model и release
  изменения требуют review CODEOWNERS.
- Изменения приходят через небольшие тематические PR с зелёными architecture,
  lint, TypeScript, unit/E2E и secret-scan gates.
- Для внешнего вклада обязательны CLA и `Signed-off-by` (DCO). CLA отвечает за
  право dual-license, DCO — за подтверждение происхождения конкретного вклада.
- Security-уязвимости отправляются только через private vulnerability reporting
  по `SECURITY.md`.

### Прозрачность решений

- Значимые продуктовые/архитектурные решения фиксируются ADR/RFC до большого
  diff.
- Roadmap показывает направление, но не обещает конкретную дату.
- Release notes различают community contributions, security fixes и breaking
  changes.
- Maintainer права выдаются по устойчивому качественному вкладу, а доступ к
  production/signing остаётся отдельной минимальной ролью.

## 6. Security и supply chain для публичного проекта

Уже обязательны: full-history Gitleaks, Dependabot, pinned GitHub Actions,
least-privilege workflow permissions, CODEOWNERS и `SECURITY.md`. Дополнительно
в настройках GitHub должны быть включены:

- secret scanning и push protection;
- private vulnerability reporting;
- Dependabot alerts/security updates;
- защита `master` с обязательными checks и review CODEOWNERS;
- protected release environment для signing/CDN secrets;
- MFA/passkeys у maintainers и владельцев production-провайдеров.

Для релизов следующий этап — SBOM, dependency-license inventory, provenance и
подписанные checksum/артефакты для каждой платформы.

## 7. Порядок внедрения

1. Ownership и asset audit.
2. Выбор владельцем варианта лицензии.
3. Legal review текстов и contributor model.
4. Одним PR добавить `LICENSE`, `TRADEMARKS.md`, `CONTRIBUTING.md`, CLA/DCO bot,
   `THIRD_PARTY_NOTICES.md` и asset manifest policy.
5. Включить обязательные GitHub settings и проверить их отдельным audit.
6. Только затем анонсировать Voople как open-source проект и принимать внешние
   feature contributions.

## 8. Критерий готовности

Стратегия считается внедрённой не по наличию файла `LICENSE`, а когда понятны
владелец прав, границы кода/бренда/ассетов, правила внешнего вклада, обязанности
по зависимостям, security disclosure и процесс выпуска официальных артефактов.
